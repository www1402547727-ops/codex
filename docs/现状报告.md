# 多机构化改造：第 0 步现状报告

检查日期：2026-10-28
检查范围：`app.py`、`course_management.py`、`user_management.py`、`cloud_store.py`、`teacher_registry.py`、`admin_console.py`，以及本地旧数据库 `data/scores.db` 的表结构。
检查方式：只读检查，没有修改业务代码，没有读写线上数据库。

> 说明：本地 `data/scores.db` 是旧快照，不代表线上真实数据；线上真实数据在 Supabase。以下结论主要来自代码和本地表结构，未使用任何真实学生数据。

## 一、结论摘要

1. 当前确实是多老师平台，但隔离方式是**每位老师一份独立 SQLite 文件**，不是在同一张表里按 `teacher_id` 过滤。
2. 目前没有机构层：没有 `organizations` 表，没有 `org_id`，没有 `org_admin` 角色，也没有平台级统一审计表。
3. 当前“管理员”不是独立的平台角色，而是老师名册里的 `is_admin` 标记；现有管理员账号同时是一个老师账号，登录后仍能进入课程、学生、成绩等内容页。
4. 当前管理员可以查看其他老师的学生姓名、学校、年级、班级和考试摘要，不符合任务书“平台管理员默认只看运营概览”的要求。
5. 学生页面查询本身会按自己的 `student_id` 取成绩，但图片/PDF 的辅助函数只按当前老师的图片目录取文件，没有校验“这个文件是否属于当前学生”。这是第 1 步必须测试和修复的越权风险。
6. 当前有登录尝试表和老师库内的简单审计表，但没有统一审计表，也没有记录管理员代入查看、导出、删除等平台级操作。
7. 任务书要求的两个试卷保存修复目前仍未推送上线：本地 `main` 比 `origin/main` 多 2 个提交，线上仍是旧版。必须先上线并验证，不能直接进入机构化第 1 步。

## 二、第 1 项：多老师隔离是怎么实现的

### 2.1 老师身份和数据路径

老师身份主要记录在 `teacher_registry.py` 管理的 `teachers.json` 中，而不是在每张业务表里放一个老师 ID。

名册结构大致为：

- `teachers`：老师列表
  - `username`：登录账号
  - `display_name`：显示名
  - `slug`：数据标识，用来拼数据库和图片路径
  - `active`：是否启用
  - `is_admin`：是否为当前管理员
  - `created_at`、`note`
  - 运行中可能还有 `stats`、`last_active`
- `usernames`：登录名到 `slug` 的路由表
- `settings`：平台级开关，例如是否允许老师给自己的学生开账号

云端路径规则：

| 内容 | 默认老师（老数据） | 其他老师 |
|---|---|---|
| 数据库 | `database/scores.db` | `database/<slug>/scores.db` |
| 图片/PDF | `photos/<文件名>` | `photos/<slug>/<文件名>` |
| 每日备份 | `backups/<日期>/scores.db` | `backups/<日期>/<slug>/scores.db` |

### 2.2 登录和切库

1. 登录前先读 `teachers.json`，把登录名转换成 `slug`。
2. `app.activate_database(slug)` 只准备该 `slug` 对应的数据库。
3. 当前会话把 `db_slug` 和 `db_path` 写入 `st.session_state`。
4. `course_management` 和 `user_management` 的 `_db_path()` 优先读取会话里的 `db_path`。
5. 管理员跨老师操作时，`admin_console` 显式使用目标 `slug` 的 `db_path` 和 `object_path`。

因此，当前的“老师隔离”是**文件级隔离 + 会话级路径隔离**，不是数据库行级隔离。

### 2.3 哪些表有老师字段

业务表都没有 `teacher_id` 或 `org_id`。老师归属由“当前打开的是哪一份数据库文件”决定。

目前能看到的表：

| 表/视图 | 作用 | 是否有老师字段 |
|---|---|---|
| `students` | 学生档案 | 否 |
| `classes` | 班级 | 否 |
| `class_members` | 班级和学生关系 | 否 |
| `schedule` | 旧版每周固定排课 | 否 |
| `plans` | 具体课程/排课 | 否 |
| `lessons` | 实际授课记录 | 否 |
| `exams` | 考试 | 否 |
| `exam_categories` | 考试分类 | 否 |
| `scores` | 成绩 | 否 |
| `app_migrations` | 一次性迁移记录 | 否 |
| `users` | 老师/学生账号 | 否 |
| `user_login_attempts` | 登录尝试 | 否 |
| `user_audit_log` | 老师库内审计 | 否 |
| `one_to_one_students` | 一对一学生及课时 | 否 |
| `legacy_one_to_one_map` | 旧版一对一班级映射 | 否 |
| `hour_transactions` | 课时续费/调整流水 | 否 |
| `teaching_locations` | 授课地点 | 否 |
| `location_settlements` | 按地点结算记录 | 否 |
| `v_lessons` | 授课记录视图 | 否 |

`teachers.json` 是当前唯一的平台级老师名册，不是 SQLite 表。

### 2.4 需要特别注意的隔离风险

1. 任何调用者只要拿到另一位老师的 `db_path`，就能直接读取那份数据库；当前没有函数级权限层统一拦截。
2. `_course_by_id`、`_get_user`、`student_report` 等函数按 id 取数据，不会再次确认这个 id 是否属于当前老师；安全性依赖“调用时使用正确数据库”。
3. `app.py` 里有模块级 `DB`、`PHOTOS` 等变量；虽然 `activate_database` 会按会话设置它们，且 `cm/um` 优先读 `st.session_state`，但第 1 步仍应做并发会话和直接函数调用测试。
4. `teachers.json` 的写入是本地 JSON 文件，不是事务型平台数据库；机构化后多个管理操作同时写名册的风险会增加。

## 三、第 2 项：所有读写数据库函数中哪些没有老师过滤

### 3.1 先说明

因为当前是“一老师一库”，绝大多数 SQL 本来就不带 `teacher_id`。这不是单纯的漏写，而是现有架构的前提。

真正需要检查的是：

- 这个函数是否只能通过当前会话的 `db_path` 访问；
- 是否能被传入另一位老师的数据库路径；
- 是否能按一个外部 id 直接读到别人的行；
- 学生页面是否在 SQL 层按自己的 `student_id` 限定。

### 3.2 `app.py`

以下函数包含数据库读写，且没有 `teacher_id` 过滤：

- 基础读写：`run`、`query`
- 迁移和合并：`_merge_duplicate_students`、`init_db`
- 课程/统计：`class_stats`、`plans_between`、`complete`、`set_status`、`plan_menu`、`page_home`、`plan_editor`、`copy_week`、`class_month_summary`
- 班级/学生：`page_classes`、`page_stats`、`student_report`、`page_students`、`page_lessons`
- 考试/成绩：`pick_exam`、`teach_map`、`exam_students`、`save_entry_changes`、`tab_entry`、`tab_analysis`、`tab_student`、`tab_manage`
- 手机“我的”：`page_me`

其中 `exam_students` 当前已经按“学校 + 年级”从 `students` 取全部在读学生，没有要求 `class_id`；如果一对一学生的学校和年级填写正确，是可以进入成绩名单的。

### 3.3 `user_management.py`

以下函数包含数据库读写，且没有 `teacher_id` 过滤：

- 基础读写：`run`
- 初始化：`init_user_db`
- 指定库创建账号：`create_account_in`（显式接收 `db_path`，用于管理员跨库操作）
- 审计和登录：`_audit`、`_record_login_attempt`、`login_lock_remaining`、`_clear_login_failures`、`_get_user_by_username`、`_get_user`、`authenticate`
- 账号页面：`page_account`、`_create_student_account`、`_delete_student_account`、`page_user_admin`
- 学生页面：`_student_courses`、`page_student_scores`

`_student_courses` 和 `page_student_scores` 会按当前登录学生的 `student_id` 过滤，但它们仍然是在当前老师数据库内过滤，不是跨老师过滤。

### 3.4 `course_management.py`

以下函数包含数据库读写，且没有 `teacher_id` 过滤：

- 基础读写：`run`
- 迁移/建表：`_backfill_one_to_one_students`、`init_course_db`
- 课程查询：`_courses_between`、`_course_by_id`、`_class_options`、`_one_options`、`_location_options`
- 课程写入：`_validate_course`、`_sync_attendance`、`save_course`、`complete_course`、`uncomplete_course`、`delete_course`、`copy_week`
- 课时：`add_hour_transaction`、`update_initial_hours`、`one_to_one_summary`、`hour_ledger`
- 地点和结算：`location_month_summary`、`location_detail_summary`、`location_settlement_summary`、`mark_location_settled`、`unmark_location_settled`、`location_management_summary`
- 班级统计：`class_month_summary`、`_class_month_detail`
- 页面中的查询：`_render_today`、`page_targets`、`page_stats`

`_course_by_id`、`save_course`、`complete_course`、`uncomplete_course`、`delete_course` 都只按课程 id 操作；如果调用方把别的数据库路径传进来，没有额外的权限校验。

### 3.5 `admin_console.py`

以下函数会跨老师访问数据：

- `_teacher_db(slug)`：按 slug 取目标老师数据库
- `_read(db, sql, params)`：在指定数据库上直接执行 SQL
- `create_teacher`：创建新老师库、账号和名册
- `rename_teacher`：改目标老师数据库里的账号
- `reset_teacher_password`：改目标老师密码
- `set_teacher_active`：改名册里的启用状态
- `teacher_students`：读取目标老师学生名单
- `create_student_account`：在目标老师库里开学生账号
- `page_admin`：遍历所有老师并展示学生、班级、考试摘要

这些函数确实显式传了目标路径，这是正确的；但它们没有机构边界、理由、同意记录、只读限制或平台级审计。

### 3.6 `teacher_registry.py` 和 `cloud_store.py`

`teacher_registry.py` 中：

- `_read_db_accounts`：只读指定数据库的账号
- `compute_stats`：只读指定数据库的统计
- `note_stats`：更新名册中的统计和最近使用时间

它们没有 `teacher_id` 过滤，但本身就是平台名册层。

`cloud_store.py` 不直接执行 SQL，只负责数据库/图片/名册的上传、下载和路径拼接。

## 四、第 3 项：照片和 PDF 的云端路径，以及学生取图校验

### 4.1 路径结构

图片和 PDF 使用同一套对象路径：

- 默认老师：`photos/<文件名>`
- 其他老师：`photos/<slug>/<文件名>`

上传逻辑：

- `app.save_photos()` 先写入当前会话的 `PHOTOS` 目录；
- `cloud_store.upload_photo()` 再按当前 `slug` 上传到对应路径。

读取逻辑：

- `app.show_photos()` 和 `user_management._show_media()` 调用 `cloud_store.ensure_local_photo()`；
- 文件名从数据库字段 `paper`、`sheet`、`exam_paper` 中以 `|` 分隔读出；
- 默认只在当前老师图片目录查找，没有找到再从当前老师云端路径下载。

### 4.2 当前学生取图的校验情况

学生成绩查询会按当前学生的 `student_id` 查询 `scores`，从结果中拿到自己的 `paper`、`sheet` 和考试共用 `exam_paper`。这部分查询有学生范围限制。

但 `_show_media()` 本身只接收文件名，不接收 `student_id`，也不查询“这个文件是否属于当前学生”。当前 UI 之所以看起来只能看到自己的文件，是因为文件名来自学生自己的查询结果；一旦有人能构造或拿到同一位老师目录下的其他文件名，辅助函数本身没有第二道校验。

另外：

- `ensure_local_photo()` 使用 `Path(local_dir) / filename`；
- `photo_object_path()` 只做了 `lstrip("/")`；
- 没有统一的 `basename` 限制、`..` 路径穿越检查或文件归属校验。

因此第 1 步必须新增测试：

1. 学生 A 用学生 B 的文件名请求图片，必须被拒绝；
2. 学生 A 不能通过路径穿越读到其他目录；
3. 试卷级共用文件可以正常显示，但答题卡必须只属于当前学生；
4. PDF 和图片走同一套校验。

## 五、第 4 项：管理员查看其他老师数据的入口

### 5.1 入口

管理员入口是：

- `app.py` 中只有 `teacher_registry.teacher_entry(...).is_admin` 为真时，才把 `admin_console.page_admin` 放进导航；
- `admin_console._require_admin()` 再次检查当前用户和名册里的 `is_admin`；
- `page_admin()` 遍历 `teacher_registry.list_teachers()`，对每位老师调用 `_teacher_db(slug)` 和 `_read(...)`。

### 5.2 当前能看到什么

在“查看数据”页签里，当前可以看到：

- 学生姓名、学校、年级、状态、学生账号；
- 班级名称、年级、类型；
- 考试名称、日期、成绩条数。

在“开学生账号”页签里，可以替目标老师创建学生账号。
在“管理”页签里，可以停用/启用老师、改老师登录账号、重置老师密码。

### 5.3 与任务书的差距

当前实现不符合以下目标：

- 平台管理员默认只能看运营概览，不能随手看学生姓名、学校、班级、考试摘要；
- 没有“选择机构 → 选择老师 → 填理由 → 勾选已获机构同意 → 临时只读进入”的流程；
- 没有红色只读横幅；
- 没有 30 分钟自动退出；
- 没有管理员代入查看的开始/结束审计；
- 没有机构管理员查看“平台方访问记录”的页面；
- 没有机构边界，管理员看到的是全部老师。

## 七、第 6 项：账号角色字段，以及阿伦账号是否兼任管理员和老师

### 7.1 当前账号表

`users` 表当前字段：

- `id`
- `username`
- `password_hash`
- `role`
- `student_id`
- `active`
- `must_change_password`
- `created_at`
- `last_login`
- `note`

`role` 当前有数据库 CHECK 限制：

```text
teacher
student
```

目前没有 `org_id`，没有 `org_admin`，也没有平台管理员角色值。

### 7.2 当前管理员身份

当前“管理员”是 `teachers.json` 里的 `is_admin` 标记，不是 `users.role` 的新值。

`teacher_registry.bootstrap()` 会把现有第一位老师登记成默认老师，并标记：

```text
is_admin = True
slug = default
```

之后 `app.py` 根据这个标记显示“账号管理”和“总后台”。因此，现有管理员账号本质上是：

```text
老师账号（users.role = teacher）
+ 名册里的管理员标记（teachers.json: is_admin = true）
```

所以当前确实是**同一个账号同时承担管理员和老师**，与任务书“平台管理员账号不兼任老师”不一致。

### 7.3 迁移建议（仅建议，本步不执行）

不能在现有 `users.role` 的 CHECK 约束上直接增加 `org_admin`，因为 SQLite 不能原地扩展 CHECK；重建表又违反“不删表、不删字段”的铁律。

建议采用兼容方案：

1. 保留 `users.role` 的 `teacher/student` 不变；
2. 新增机构归属字段，例如 `users.org_id`；
3. 新增权限标记表或字段，例如 `user_org_roles`，表示“本机构管理员”；
4. 把现有管理员账号拆成：
   - 一个独立的平台管理员账号（只看运营概览）；
   - 一个普通老师账号（承接现有教学数据）；
5. 拆分前先做数据备份和登录路由演练，不能直接改线上。

具体是“角色字段”还是“独立权限表”，需要阿伦确认。我的建议是**新增独立权限关系表**，不要改现有 `role` 的 CHECK。

## 九、成绩模块现状补充

### 9.1 当前关系

- `exams` 仍有旧的 `class_id` 字段；
- `scores` 仍然以 `student_id` 和 `exam_id` 关联；
- 同一个 `exam_id + student_id` 有唯一索引，能防止重复成绩；
- 成绩状态支持 `未录入`、`已录入`、`缺考`；
- 空成绩不会被自动当成 0 分；
- 考试可以填写学校、年级、科目、满分；
- 成绩录入名单优先按学校和年级取 `students`，班级不是必要条件。

### 9.2 一对一学生为什么可能无法录入

从当前代码看，一对一学生并不是因为 `one_to_one_students` 表被排除而不能录入。只要：

1. 该学生有一条 `students` 档案；
2. `students.school` 和 `students.grade` 与考试设置一致；
3. 考试填写了学校或年级；
4. 学生状态为 `在读`；

就会进入成绩名单。

实际最常见的原因是：

- 一对一学生的学校/年级没有填；
- 考试的学校/年级没有填；
- 使用的是没有学校/年级字段的旧考试，只能回退到 `class_id` 班级名单；
- 学生档案和一对一记录没有正确关联到同一个 `students.id`。

第 1 步应专门测试这些数据条件，不要先改业务逻辑。

## 十、和任务书不一致、需要阿伦决定的地方

### 10.1 是否先上线两个试卷修复

当前本地 `main` 比 `origin/main` 多两个提交：

- `0af6eef`：学生端只上传试卷、未录成绩时也能看到试卷；
- `1cdd6ed`：上传试卷后加强保存校验并显示上传数量。

线上目前还是旧版。任务书明确要求“邀请机构前先确认试卷保存修复上线并验证”。建议先完成上线和人工验证，再进入第 1 步。

### 10.2 管理员是否拆成两个账号

需要确认：

- 阿伦的现有教学数据继续归哪个老师账号；
- 新的平台管理员账号叫什么；
- 旧管理员账号拆分后，现有登录名和密码怎么迁移；
- 学生/老师是否需要重新登录。

在没有确认前，不应直接改线上账号。

### 10.3 机构数据放在哪里

当前老师数据是“一老师一库”。机构层天然跨老师，不能只把 `organizations` 表塞进每位老师的库，否则机构信息会重复，机构管理员也无法统一管理。

建议在第 2 步前先定一个平台级存储方案，例如：

- 新建一个小型平台数据库，存机构、机构成员、平台管理员、统一审计和同意记录；
- 老师教学数据继续放在各自的 `scores.db`；
- 机构管理员通过平台层路由到本机构老师的库，并在函数入口强制校验机构边界。

这会比直接扩展 `teachers.json` 更稳，但需要同时设计备份、恢复和 Supabase 对象路径。请阿伦确认是否接受新增一个平台级数据库。

### 10.4 机构管理员角色怎么实现

建议不要改 `users.role` 的 CHECK，改用：

- `users.org_id` 表示归属机构；
- 独立的 `user_org_roles` 或权限标记表示 `org_admin`；
- 老师仍然是 `teacher`，学生仍然是 `student`；
- 个人机构老师可以同时拥有本机构的 `org_admin` 权限，但界面上不显示机构管理入口。

### 10.5 学生媒体文件权限

第 1 步必须修复：

- 学生只能读取自己的答题卡；
- 试卷共用文件按考试范围校验；
- PDF 和图片统一校验；
- 文件名只允许 basename，拒绝 `..` 和跨目录路径。

### 10.6 备份保留

当前 `cloud_store.save_database()` 会创建每日备份，但没有看到 30 天清理逻辑。第 7 步实现前，说明页不能承诺“最长保留 30 天”。

## 十一、建议的下一步
